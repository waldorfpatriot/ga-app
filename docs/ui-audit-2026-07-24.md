# UI Audit

**Product:** Gesamtausgabe  
**Date:** 2026-07-24  
**Platforms reviewed:** iPhone, iPad-responsive code paths, and macOS  
**Surfaces reviewed:** Public reader and internal developer catalog  
**Audit type:** Rendered UI, responsive/accessibility review, and static SwiftUI review

## Executive Summary

The app has a strong native foundation: its restrained serif reader, selectable text, system controls, adaptive split-view architecture, and download/offline states are appropriate for a long-form reading product.

It is not release-ready yet. Two launch-configuration defects are visible before a user reaches the interface:

1. The iOS target has no launch-screen configuration, so it renders in a legacy letterboxed viewport with large black areas.
2. The project has no AppIcon or asset catalog, so the installed app displays a blank placeholder icon.

The next most important work is adaptive layout. Accessibility XXXL exposes severe truncation and control-layout problems, while the default 840-point Mac window compresses the library and passage columns and lets global toolbar content obscure the reading surface.

## Scope and Validation

The audit included:

- Building and launching the `GA iOS` target on an iPhone 17-class simulator.
- Rendering the reader at the standard Dynamic Type size.
- Rendering the reader at `accessibility-extra-extra-extra-large`.
- Building and launching the `GA Mac` target at its default 840-point window width.
- Loading the real local catalog backend and full GA 004 content.

## Strengths to Preserve

- Native SwiftUI lists, search, buttons, progress indicators, and split-view navigation.
- Calm serif typography that gives the reader an appropriate literary character.
- Selectable article and annotation text.
- Reader text scaling persisted through `AppStorage`.
- Use of `ScaledMetric` for reader body and title sizes.
- System colors and materials that adapt to appearance changes.
- Clear idle, downloading, loaded, failed, retry, and offline data states.
- A focused reader-safe catalog separate from the internal developer overview.
- Side-by-side/stacked proofing layouts already structured with `ViewThatFits`.

## Prioritized Findings

### P0 — Release Blockers

#### UI-001: Missing iOS launch screen causes legacy letterboxing

**Observed**

The iPhone build launches against a black background with the app constrained to a short, rounded white viewport. The generated `Info.plist` contains neither `UILaunchScreen` nor `UILaunchStoryboardName`.

**Impact**

- The product looks broken on first launch.
- A substantial portion of the screen is unusable.
- Compact layouts and Dynamic Type receive much less room than intended.
- Startup briefly presents an entirely black screen.

**Location**

- `apple/GA.xcodeproj/project.pbxproj:291`
- `apple/GA.xcodeproj/project.pbxproj:316`

**Recommendation**

Configure a generated launch screen for both iOS build configurations, or add a dedicated launch-screen file. With the generated Info.plist approach, use the appropriate `INFOPLIST_KEY_UILaunchScreen_*` build setting and verify the built Info.plist.

The launch screen should closely match the first app background without branding or static text.

**Acceptance criteria**

- The app uses the complete iPhone and iPad viewport.
- No black letterboxing appears.
- Light and dark launches transition cleanly into the first screen.
- The built Info.plist contains a valid launch-screen declaration.

References:

- [Apple: Specifying your app’s launch screen](https://developer.apple.com/documentation/xcode/specifying-your-apps-launch-screen)
- [Apple HIG: Launching](https://developer.apple.com/design/human-interface-guidelines/launching)

#### UI-002: Missing AppIcon and asset catalog

**Observed**

The installed app displays a blank translucent placeholder icon. The project references an `AccentColor` name but contains no `.xcassets` catalog and no configured AppIcon.

**Impact**

- The app is difficult to recognize on the Home Screen, in search, and in system settings.
- The product has no consistent visual identity across iOS and macOS.
- This is not acceptable for distribution.

**Location**

- `apple/GA.xcodeproj/project.pbxproj:294`
- `apple/GA.xcodeproj/project.pbxproj:319`
- `apple/GA.xcodeproj/project.pbxproj:344`
- `apple/GA.xcodeproj/project.pbxproj:371`

**Recommendation**

Add an asset catalog or Icon Composer output with:

- A layered 1024×1024 app icon.
- Default, dark, clear, and tinted appearance validation.
- A tested accent color for light, dark, and increased-contrast modes.
- Consistent icon configuration for iOS, iPadOS, and macOS.

Reference:

- [Apple HIG: App icons](https://developer.apple.com/design/human-interface-guidelines/app-icons/)

### P1 — High Priority

#### UI-003: Accessibility Dynamic Type breaks primary layouts

**Observed**

At Accessibility XXXL, the selected work title fills most of the available viewport. Several code-level constraints will remain problematic even after the launch-screen defect is fixed:

- Reader and developer work titles are capped at two lines.
- Type and proofing summaries are capped at one line.
- Previous, count, and Next are forced into one horizontal row.
- The proofing section picker forces a 220-point minimum toolbar width.
- Status-pill groups have no accessibility-size fallback.

**Location**

- `apple/GA/LibraryScreen.swift:372`
- `apple/GA/LibraryScreen.swift:404`
- `apple/GA/LibraryScreen.swift:536`
- `apple/GA/LibraryScreen.swift:653`
- `apple/GA/LibraryScreen.swift:714`
- `apple/GA/ReaderView.swift:145`

**Recommendation**

- Read `dynamicTypeSize` and switch to expanded rows at accessibility sizes.
- Remove restrictive line limits for primary identifiers at accessibility sizes.
- Use `ViewThatFits` or vertical navigation controls for Previous/Next.
- Keep important controls at least 44×44 points.
- Use a compact menu representation for the proofing picker on narrow screens.

References:

- [Apple HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility/)
- [Apple HIG: Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- [Apple HIG: Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)

#### UI-004: Compact launch bypasses the library

**Observed**

A default volume is selected immediately and `preferredCompactColumn` starts at `.content`. On iPhone, a new user lands in the first work’s detail view rather than the library.

**Impact**

- The product appears to contain only one work.
- Users do not receive an overview of the available collection.
- The behavior resembles “continue reading,” but no reading-position state supports that intent.

**Location**

- `apple/GA/LibraryScreen.swift:31`
- `apple/GA/LibraryScreen.swift:34`
- `apple/GA/LibraryScreen.swift:60`

**Recommendation**

Start compact navigation at `.sidebar`. Advance to `.content` only after an explicit work selection. A future persisted reading position may legitimately open the reader, but it should be presented as an intentional resume flow.

#### UI-005: Passage changes retain the previous scroll position

**Observed**

The reader keeps one `ScrollView` alive while Previous/Next and passage selection only change `passageID`. A new passage can therefore appear near the previous passage’s scroll offset instead of at its beginning.

The rendered Mac pass opened a selected passage partway through its text, confirming the practical impact of the persistent scroll state.

**Location**

- `apple/GA/ReaderView.swift:29`
- `apple/GA/ReaderView.swift:145`

**Recommendation**

Wrap the article in `ScrollViewReader`, add a stable top anchor, and scroll to it when `passageID` changes. Alternatively, key the scroll container with the selected passage ID.

#### UI-006: Search and filtering can leave a hidden stale selection

**Observed**

The visible list uses `filteredVolumes`, while the detail pane resolves its selection from the complete hydrated or catalog collection. Search or developer filtering can remove the selected item from the visible list while leaving its detail on screen.

**Impact**

- The list and detail disagree.
- Empty search results can still show unrelated detail content.
- The developer segmented filter does not reliably communicate current scope.

**Location**

- `apple/GA/LibraryScreen.swift:47`
- `apple/GA/LibraryScreen.swift:53`
- `apple/GA/LibraryScreen.swift:238`
- `apple/GA/LibraryScreen.swift:246`

**Recommendation**

Reconcile selection whenever the query or filter changes:

- Keep the selection if it remains visible.
- Otherwise select the first filtered result or clear the detail.
- Derive displayed detail from the filtered collection when the filter defines the current scope.

#### UI-007: The default Mac window compresses navigation and obscures content

**Observed**

At the default 840-point window width:

- The library column truncates most work titles.
- The passage column truncates nearly every section title.
- The green catalog status is clipped.
- Reader controls and the library search field share a floating top toolbar over the article.
- Article text begins underneath the toolbar region.

**Location**

- `apple/GA/LibraryScreen.swift:60`
- `apple/GA/LibraryScreen.swift:73`
- `apple/GA/ReaderView.swift:60`

**Recommendation**

- Set minimum and ideal widths with `navigationSplitViewColumnWidth`.
- Give the library and passage columns enough width for meaningful identifiers.
- Place library search firmly within the sidebar context.
- Consolidate font and page controls into a Reading Settings menu.
- Ensure the reader header/content receives sufficient top inset below the toolbar.

#### UI-008: Reader toolbar exposes unfinished and competing actions

**Observed**

The reader promotes five toolbar controls:

- Smaller Text
- Larger Text
- Page Numbers
- Bookmark
- Facsimile

Bookmark and Facsimile are permanently disabled placeholders.

**Impact**

- Compact toolbar space is crowded.
- Disabled dead ends weaken confidence in implemented controls.
- Font buttons receive more prominence than article navigation.

**Location**

- `apple/GA/ReaderView.swift:60`

**Recommendation**

- Remove unavailable controls until their features exist.
- Group font scale and page-number visibility into Reading Settings.
- Keep frequently used reading actions visible only when there is adequate space.

#### UI-009: Developer search promises unsupported status matching

**Observed**

The prompt says “Search GA, title or status,” but `searchBlob` excludes publication and proofing status. Queries such as “published,” “queue,” and “AI checked” can produce empty results.

**Location**

- `apple/GA/LibraryScreen.swift:278`
- `apple/GA/Models.swift:298`

**Recommendation**

Add publication labels, proofing labels, and useful synonyms to the search index, or change the prompt to accurately describe searchable fields.

#### UI-010: Proofing view is not an effective diff

**Observed**

The proofing screen places complete original and normalized blocks on faint red and green backgrounds. It does not identify changed words or lines, align corresponding changes, or synchronize scrolling. Highly compressible columns may also remain side by side at unreadable widths before `ViewThatFits` selects the vertical fallback.

**Location**

- `apple/GA/LibraryScreen.swift:618`
- `apple/GA/LibraryScreen.swift:670`

**Recommendation**

- Compute changed blocks or word/line-level differences.
- Visually emphasize only meaningful changes.
- Preserve surrounding context without coloring entire documents.
- Use an explicit width threshold or minimum diff-column width.
- Consider synchronized scrolling for long side-by-side comparisons.

### P2 — Medium Priority

#### UI-011: Reading hierarchy emphasizes the repeated work title

The work title is the largest reader heading, while the current section title is a secondary-colored headline. The section is the changing, task-relevant context and should receive stronger emphasis.

**Location**

- `apple/GA/ReaderView.swift:321`

**Recommendation**

Use the work title as a smaller eyebrow or navigation subtitle and promote the passage/chapter title to the primary article heading.

#### UI-012: VoiceOver semantics are incomplete

**Issues**

- German reading text is not explicitly exposed with German speech-language metadata.
- Work and passage headings have no accessibility heading traits.
- Selected passages rely on a tinted checkmark without an `isSelected` trait.
- Async catalog/download state changes have no deliberate announcement.
- Sanity-check icons rely heavily on color and are not combined into a coherent status element.

**Location**

- `apple/GA/ReaderView.swift:281`
- `apple/GA/ReaderView.swift:327`
- `apple/GA/LibraryScreen.swift:493`
- `apple/GA/LibraryScreen.swift:740`
- `apple/GA/LibraryScreen.swift:774`

**Recommendation**

Add language-aware speech behavior, heading traits, selection traits, meaningful status values, and announcements for download/offline transitions. Validate manually with VoiceOver and Voice Control.

#### UI-013: Annotation and passage-navigation targets are too small

Annotation markers such as “(1)” become inline Text links whose hit area is close to the glyph bounds. The Previous/Next buttons also have label-sized hit regions with no enforced minimum height.

**Location**

- `apple/GA/ReaderView.swift:150`
- `apple/GA/ReaderView.swift:249`
- `apple/GA/ReaderView.swift:281`

**Recommendation**

- Provide at least 44×44-point interactive targets.
- Give annotation links descriptive spoken labels such as “Note 1.”
- Consider a dedicated notes list or accessibility rotor.
- Include neighboring section titles in Previous/Next controls.

#### UI-014: Connection status consumes permanent prime space

“Reader catalog loaded from server” remains in the first sidebar section and is rendered as a small green caption. On the default Mac window it is truncated and low contrast. The offline state stores an error string but does not surface useful detail or a direct retry action.

**Location**

- `apple/GA/LibraryScreen.swift:63`
- `apple/GA/LibraryScreen.swift:736`

**Recommendation**

- Remove or automatically dismiss the success state.
- Show a friendly offline banner only when relevant.
- Provide concise error context and Retry.
- Keep primary status text in a standard label color rather than relying on green.

#### UI-015: Status pills flatten unrelated meanings

Language, work type, availability, publication state, proofing state, and summary counts all use the same thin-material capsule. “Download” looks like a button even when it is only a status, and long developer statuses have no adaptive layout.

**Location**

- `apple/GA/LibraryScreen.swift:376`
- `apple/GA/LibraryScreen.swift:408`
- `apple/GA/LibraryScreen.swift:440`
- `apple/GA/LibraryScreen.swift:536`
- `apple/GA/LibraryScreen.swift:707`
- `apple/GA/LibraryScreen.swift:808`

**Recommendation**

Define a small semantic status system:

- Metadata: plain secondary labels.
- Availability: icon plus “Downloaded” or “Not downloaded.”
- Workflow state: explicit status text with restrained color.
- Counts: summary text rather than pills.

#### UI-016: Terminology and interface language are inconsistent

The model includes books, lecture cycles, lectures, essays, and education works, but reader copy repeatedly uses “Books,” “Book Text,” and “Downloading book.” The interface is predominantly English around German content, with isolated German strings such as “Anmerkung.”

**Location**

- `apple/GA/LibraryScreen.swift:67`
- `apple/GA/LibraryScreen.swift:453`
- `apple/GA/ReaderView.swift:197`
- `apple/GA/ReaderView.swift:305`
- `apple/GA/Models.swift:3`

**Recommendation**

- Use “Works,” “Volumes,” “Sections,” and “Text” consistently.
- Choose and document the source interface language.
- Add a String Catalog.
- Treat German as a first-class localization for the intended audience.

#### UI-017: Empty subtitles can create phantom spacing

Reader detail always inserts a subtitle view, while API decoding defaults absent subtitles to an empty string. Developer detail already guards this case.

**Location**

- `apple/GA/LibraryScreen.swift:430`
- `apple/GA/Models.swift:261`

**Recommendation**

Only render the subtitle view when the trimmed subtitle is non-empty.

#### UI-018: There is no UI or accessibility regression coverage

The Xcode project contains only the iOS and Mac app targets. There is no UI-test or snapshot-test target.

**Missing coverage**

- Compact and regular widths.
- Default and Accessibility XXXL Dynamic Type.
- Light, dark, and increased-contrast appearances.
- Long German titles and metadata.
- VoiceOver labels, headings, and selected state.
- Search/filter selection reconciliation.
- Passage scroll-to-top behavior.
- Download success, failure, retry, and offline fallback.
